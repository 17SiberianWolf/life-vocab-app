# 架构决策记录（ADR）

> **ADR（Architecture Decision Record）**：记录重大技术决策的**背景、备选方案、选择理由与后果**。
> 目的不是"记录做了什么"，而是"**记录为什么这么选、放弃了什么**"——防止半年后重蹈覆辙。

## ADR-001：采用纯前端单文件架构，不用构建框架

- **状态**：✅ 已采纳（2026-08，阶段 1）
- **背景**：需要一款个人英语词汇学习工具，作者是工控/机器视觉工程师（C# 背景），前端非主业。
- **备选方案**：
  | 方案 | 优点 | 缺点 |
  |---|---|---|
  | React + Vite | 组件化、生态好 | 需要 node_modules、构建链、依赖维护；个人项目负担重 |
  | Vue 3 | 上手快 | 同上 |
  | **原生 JS + 单 HTML** | 零依赖、双击即开、可离线、易分发 | 无类型检查、大文件（数千行）难维护 |

- **决策**：**原生 JS + 单文件 HTML**。
- **理由**：
  1. 目标用户只有作者本人 + 少量设备，**分发简易性 > 工程规范性**
  2. 数据只有 3000 余条，不需要虚拟列表等复杂优化
  3. 单文件可直接 Email/网盘分享，不依赖任何运行时
- **后果**：
  - ⚠️ `index.html` 达 900KB，源码必须靠 `build_index.py` 生成，不能直接手改
  - ⚠️ 无组件化，视图切换靠手写 `show()`；**后期确实因此出了"切视图不停游戏"的 bug**（见 ADR-008）
  - ✅ 缓解措施：源码拆到 `lib/*.js`（独立 IIFE）+ `build_index.py` 主模板

## ADR-002：数据内联进 HTML，而非运行时 fetch JSON

- **状态**：✅ 已采纳
- **背景**：词库 3230 条，需要离线可用。
- **备选**：① `<script>window.APP_DATA={...}</script>` 内联；② `fetch('cards.json')`；③ IndexedDB 存词库
- **决策**：**构建时内联**（`build_index.py` 把 JSON 嵌入 HTML）
- **理由**：`file://` 协议下 `fetch` 会被 CORS 阻断，双击打开就废了；IndexedDB 存词库增加复杂度且首屏慢
- **后果**：
  - ⚠️ HTML 体积大（900KB / gzip 208KB）。可接受：Cloudflare 免费 CDN，实测首屏 < 2s
  - ✅ 换取了"双击即开 + 完全离线"的核心体验

## ADR-003：跨端方案选择 Web + PWA，放弃 Tauri

- **状态**：✅ 已采纳（2026-09，阶段 5 立项）
- **背景**：作者希望"在任意电脑上都能使用"，考虑过打包桌面应用。
- **备选**：
  | 方案 | 优点 | 缺点 |
  |---|---|---|
  | **Tauri（Rust 壳）** | 真桌面应用、体积小、可访问系统 API | 需 Rust 工具链；每平台单独打包；更新要重新分发 |
  | Electron | 生态成熟 | 体积 100MB+，杀鸡用牛刀 |
  | **Web + PWA** | 一套代码全平台、更新即生效、可"安装"到桌面 | 受浏览器能力限制（如文件系统） |

- **决策**：**Web + PWA**
- **理由**：
  1. 应用能力需求（发音、麦克风、本地存储）**浏览器全都能满足**，Tauri 带来的系统 API 用不上
  2. 更新体验天差地别：PWA 改完 push 一次，所有设备下次打开就是新版；桌面应用要重新分发安装包
  3. 作者无 Rust/C++ 工具链，Tauri 的构建排障成本高
- **后果**：
  - ⚠️ 依赖 Service Worker 缓存 → **必须每次发版 bump `CACHE_NAME`**（见 ADR-009）
  - ⚠️ iOS Safari 的 PWA 支持有历史坑（已通过 `manifest` + `apple-touch-icon` 缓解）

## ADR-004：云同步后端选 Supabase

- **状态**：✅ 已采纳
- **背景**：多设备需要同步学习进度。
- **备选**：
  | 方案 | 优点 | 缺点 |
  |---|---|---|
  | 自建后端（Node + MySQL） | 完全可控 | 要买服务器、运维、备案，个人项目不可接受 |
  | Firebase | 成熟 | 国内访问不稳定 |
  | LeanCloud | 国内快 | 需实名+备案，免费额度收紧 |
  | **Supabase** | Postgres + Auth + RLS 开箱即用，免费额度充足 | 国内访问速度不稳定（节点在境外） |

- **决策**：**Supabase**
- **理由**：
  1. **RLS（行级安全）**是关键：前端直连数据库且公钥必然暴露，RLS 是唯一安全边界
  2. Auth 内置（邮箱密码、JWT），不用自己实现
  3. 免费额度（500MB DB / 5GB 流量）远超本项目需求（单人使用，数据量 < 1MB）
- **后果**：
  - ⚠️ 国内访问 Supabase API 偶发慢。**当前可接受**（同步是后台异步，不阻塞学习）；若未来恶化，可迁移到 CloudBase（数据层接口不变）
  - ⚠️ 前端明文持有 anon key（Supabase 设计如此，安全靠 RLS 而非密钥保密）→ 见 ADR-010

## ADR-005：本地存储用 IndexedDB，不用 localStorage

- **状态**：✅ 已采纳
- **背景**：需要存 3000+ 张卡的学习状态、离线同步队列。
- **备选**：`localStorage`（5MB 上限、同步阻塞主线程、只能存字符串） vs **IndexedDB**（容量大、异步、支持结构化对象）
- **决策**：**IndexedDB**（封装在 `lib/db.js`）
- **理由**：localStorage 的 `setItem` 是**同步阻塞**的，每答一题写一次会卡 UI；且 5MB 上限不利于离线队列
- **后果**：
  - ⚠️ IndexedDB API 是回调式的，代码比 localStorage 繁琐 → 已在 `lib/db.js` 封装成 Promise 接口
  - ✅ 支持了离线队列（`pending_ops`）能力

## ADR-006：部署平台选 Cloudflare Pages（经历 Vercel、CloudBase 两次失败）

- **状态**：✅ 已采纳（最终方案）
- **背景**：需要国内能访问、免备案、免费的静态托管。
- **演进过程（三次试错，务必阅读）**：

  | 平台 | 结果 | 失败原因 |
  |---|---|---|
  | **Vercel** | ❌ 失败 | ① 构建环境无 `python3`，`build_index.py` 执行失败 → 502；② 即便改成纯静态，**`.vercel.app` 域名在大陆被限制访问** |
  | **腾讯云 CloudBase** | ❌ 放弃 | ① 控制台改版频繁、入口深、文档零散、无有效客服；② 新环境创建后长时间"环境不可用"；③ 免费版静态托管权限疑似被锁，需升级 19.9 元/月套餐 |
  | **Cloudflare Pages** | ✅ 成功 | `*.pages.dev` 国内可访问；免费；连 GitHub 自动部署 |

- **决策**：**Cloudflare Pages**
- **关键教训（必记）**：
  1. ⚠️ **Cloudflare 有 Workers 和 Pages 两个易混淆产品**。入口「Create application」→ 默认走 **Workers**（`npx wrangler deploy`），部署到 `*.workers.dev`（**国内被墙**）。
     **必须点界面最底部的灰色小字链接 `Continue to Pages`** 才是 Pages 流程。
  2. ⚠️ 配置：**Build command 留空 + Build output directory = `dist`**。
     填 `python3 build_index.py` 会因构建环境无 python3 而失败（Vercel 的坑重演）。
     → 改为**把 `dist/` 提交进 git**，让 Cloudflare 直接部署成品，零构建依赖。
- **后果**：
  - ⚠️ 每次发版需要 `git push` 触发自动部署，约 1–2 分钟生效
  - ⚠️ `dist/` 必须提交进 git（为此从 `.gitignore` 移除了 `dist/`）—— 与"构建产物不入 git"的常规实践相反，是为绕开构建环境限制的**主动取舍**

## ADR-007：构建产物 `dist/` 提交进 git（反常规）

- **状态**：✅ 已采纳
- **背景**：Cloudflare Pages 构建环境无 python3，无法现场执行 `build_index.py`。
- **备选**：
  ① 构建环境装 python（平台不支持）
  ② 改用 JS 重写构建脚本（工作量大，收益低）
  ③ **`dist/` 提交进 git，部署时不构建**
- **决策**：**③**
- **理由**：成本最低、最稳。构建脚本仍是 Python（本地好用），部署侧零依赖。
- **后果**：
  - ⚠️ 违反"构建产物不入版本库"的常规，需在文档中显式说明（已写入 `CONTRIBUTING.md`）
  - ⚠️ **发版前必须在本地跑 `python build_index.py`**，否则推上去的是旧产物 —— 这是最容易忘的一步

## ADR-008：引入 `stopAllGames()` 视图生命周期钩子 + 回合身份校验

- **状态**：✅ 已采纳（2026-09，bug 修复 `422d5b0`）
- **背景**：退出消消乐后，仍能听到单词发音，重进游戏时单词下落变快。
- **根因**：`show()` 只切换 DOM 显示，**没有"离开视图"的停止逻辑**。导致：
  1. 消消乐 30ms 定时器继续跑
  2. 自动发音 / 落底 / 作答的 `setTimeout` 回调继续触发 → 后台持续发音、持续掉命
  3. 重进游戏时旧 interval 未清除 → **多局叠加，下落速度越来越快**
  4. 连连看/碰碰乐完成后的 `setTimeout` 会在离开后弹出 alert 并重开局
- **备选**：
  ① 在每个游戏的退出按钮里单独清理（易漏、难维护）
  ② **统一 `stopAllGames()` 钩子 + 所有异步回调加"回合身份校验"**
- **决策**：**② 双层防御**
  - 第一层：`show()` 开头调用 `stopAllGames()`，清所有回合状态 + 定时器 + `speechSynthesis.cancel()`
  - 第二层：所有延迟回调执行前先校验 `STATE.xxxRound === r`（当前回合还是不是我这一局），否则直接 return
- **理由**：第二层是**结构性防御**——即使将来新增延迟逻辑忘了进钩子，也不会后台乱跑
- **后果**：
  - ✅ 四个游戏（消消乐/碰碰乐/连连看/听音）统一修复
  - ⚠️ 约定：**今后任何 `setTimeout`/`setInterval` 回调，都必须带回合身份校验**

## ADR-009：Service Worker 采用 cache-first + 每次发版 bump CACHE_NAME

- **状态**：✅ 已采纳
- **背景**：PWA 需要离线可用，但缓存会让用户拿不到新版。
- **备选**：
  ① network-first（总是最新，但离线体验差、慢）
  ② **cache-first + 手动 bump 版本号**
  ③ stale-while-revalidate（折中，实现复杂）
- **决策**：**②**
- **理由**：词库 900KB，cache-first 能让二次访问**秒开**（这是学习工具的高频场景）；版本更新由开发者显式控制，行为可预测
- **后果**：
  - ⚠️ **铁律：每次改代码必须把 `sw.js` 的 `CACHE_NAME` 版本号 +1**，否则用户永远加载旧页面
  - ⚠️ 用户侧可能仍需 `Ctrl+F5` 才能立即拿到新版（浏览器对 SW 的更新时机有延迟）
  - 版本演进：v1 → v2 → ... → **v9（当前）**

## ADR-010：前端明文持有 Supabase anon key，安全边界靠 RLS

- **状态**：✅ 已采纳（有意识的风险接受）
- **背景**：纯前端应用无法保密任何密钥。
- **备选**：
  ① 密钥藏进后端代理（要自建后端，与 ADR-004 冲突）
  ② **接受明文，用 RLS 做唯一安全边界**
- **决策**：**②**
- **理由**：这是 Supabase 的官方推荐用法。anon key 本身设计为可公开，**安全性完全由 RLS 策略保证**
- **强制要求（不可妥协）**：
  1. 三张业务表（`cards_progress` / `user_settings` / `rec_scores`）**必须启用 RLS**
  2. 策略必须是 `auth.uid() = user_id`，覆盖 SELECT / INSERT / UPDATE / DELETE
  3. 启用 RLS 前**不得上线**（否则任何人可读写全表）
- **后果**：
  - ⚠️ 若将来新增表或改表结构，**必须同步补 RLS**，这是最高优先级的安全检查项
  - ✅ 已将检查项写入 `11-SECURITY` 与 `08-OPS` 的上线 CheckList

## ADR-011：发音走浏览器内置 TTS，剥离离线 mp3

- **状态**：✅ 已采纳（2026-09）
- **背景**：项目早期用 `edge-tts` 生成了 2992 个 mp3（61MB），卡片数据里嵌入了音频路径。
- **问题**：
  1. 61MB 音频不适合部署到 CDN（免费额度、首屏、同步都是负担）
  2. 部署到 Cloudflare 时若不上传 mp3，`<audio>` 会 404 后再兜底 TTS → 每次发音多一次失败请求
- **备选**：
  ① 上传 61MB mp3 到 CDN（体积大，且 Cloudflare Pages 有文件数/体积限制）
  ② **构建时剥离音频路径，直接走浏览器 TTS**
- **决策**：**②**，并在 `build-config.json` 加开关 `audio.embed`
- **理由**：
  - 浏览器 TTS 质量已足够（en-GB 神经网络语音）
  - 产物从 494KB 降到 344KB，部署包从 61MB 降到 365KB
  - 保留开关**可随时回退**，不破坏原有资产
- **后果**：
  - ⚠️ 发音质量依赖用户系统已装的语音包（Windows 需安装英语语音包）
  - ⚠️ 离线仍可用（TTS 是浏览器本地能力），但**音色与在线时一致**
  - ✅ `audio/` 目录仍在 `.gitignore` 中，本地可随时重新生成

## ADR-012：「今日复习」计数只统计真复习，新词走每日额度

- **状态**：✅ 已采纳（2026-09，bug 修复 `0961e1f`）
- **背景**：词库扩充到 3032 张后，首页「今日复习」徽标显示 **2293**。
- **根因**：`getDueCards()` 里 `if (!s) return true`（从未学过的新卡也算"待复习"），把 2293 张未学词全算进"今日"
- **问题**：
  1. 名不副实（按钮叫"复习"，装的却是从没见过的词）
  2. **永远做不完、永不归零** → 失去"今日完成"的反馈价值，纯劝退
  3. **性能炸弹**：SRS 页会把 2293 张全部渲染成 DOM
- **决策**：
  1. `getDueCards()` 只统计 **SRS 到期卡 + 错题**
  2. 新增**每日新词额度**（默认 10/天），跨天自动重置
  3. 徽标 > 99 显示 `99+`
- **理由**：这是 Anki / SuperMemo 等成熟 SRS 软件的通行做法——**复习与引入是两个独立概念**
- **后果**：
  - ✅ 徽标数字骤降到真实待复习量；每天有明确的"完成"反馈
  - ⚠️ 词库完整学完约需 10 个月（按 10/天）——**这是设计意图，不是缺陷**
  - 未来可考虑在设置里开放额度调整
